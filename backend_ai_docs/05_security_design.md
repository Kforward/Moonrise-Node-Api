# 05 数据安全设计

## 1. 数据分类

| 类型 | 示例 | 保护等级 |
| --- | --- | --- |
| 身份数据 | openid、设备 ID、token | 高 |
| 个人资料 | 昵称、头像、手机号、邮箱 | 高 |
| 周期数据 | 经期日期、流量、痛感、备注 | 极高 |
| 备份快照 | 用户完整数据快照 | 极高 |
| 展示数据 | 更新日志、配置枚举 | 低 |

## 2. 认证安全

- access token 短期有效。
- refresh token 只保存哈希。
- 每个设备有独立 session。
- 注销设备后对应 refresh token 立即失效。
- 微信 session key 不落库明文。

## 3. 加密策略

### 3.1 第一阶段

- 数据库磁盘加密由基础设施承担。
- 手机号、邮箱、备注、备份快照使用字段级加密或密文列。
- 服务端密钥通过环境变量或 KMS 注入，不写业务表。
- `privacy_configs` 只记录算法、模式和密钥版本。

### 3.2 后续端到端加密

- 客户端生成数据密钥。
- 服务端只保存密文、算法、nonce、key_version、content_hash。
- 当前小程序端可用的端到端密文信封为 `aes-256-cbc-hmac-sha256`：客户端用 PBKDF2-SHA256 派生加密密钥和 MAC 密钥，AES-256-CBC 加密，HMAC-SHA256 做 encrypt-then-MAC 认证；服务端只托管密文信封，不保存密钥、不解密。
- 忘记密码和设备丢失时不能假装可恢复；必须依赖恢复密钥、可信设备或用户主动备份。

### 3.3 密钥保护与恢复策略

- 后续密钥体系采用 DEK/KEK 分层：
  - DEK：客户端随机生成的数据密钥，用于加密周期数据、用户资料和备份快照。
  - KEK：由设备安全能力、PIN/密码、恢复密钥或可信设备公钥得到，只用于包裹 DEK。
- 服务端只托管 key wrap 元数据，例如 `wrap_type`、`algorithm`、`kdf`、`salt`、`nonce`、`wrapped_key`、`key_version`、`device_id`、`created_at` 和 `revoked_at`，不保存明文 DEK 或 KEK。
- 换机恢复只允许两条路径：
  - 旧设备仍可信且已解锁，由旧设备把 DEK 包裹给新设备公钥。
  - 用户输入恢复密钥，由客户端派生 KEK 并解包 DEK。
- 忘记 PIN/密码时：
  - 已解锁设备可重新生成 `passphrase` key wrap。
  - 有恢复密钥或可信旧设备可恢复后重新包裹。
  - 三者都没有时只能重置加密数据，服务端不能也不应提供明文恢复。
- 创建、撤销、恢复和重置 key wrap 必须写入审计日志，日志只记录 wrap 类型、密钥版本、设备 ID 和结果，不记录密钥材料。

## 4. 审计

必须写入审计日志的操作：

- 登录、刷新 token 失败过多。
- 注销设备。
- 创建、恢复、删除备份。
- 切换隐私加密模式。
- 创建、撤销或使用 key wrap 恢复。
- 批量同步失败或冲突。
- 解密失败。

## 5. 风险边界

- 当前小程序本地 AES 属于软件级保护，不等同于硬件级安全。
- 后端第一阶段也不应宣称医疗级合规。
- 后端能增强云端存储安全，但如果采用服务端可解密模式，理论上服务端仍可接触明文。
- 若要最大化隐私，应优先推进端到端加密模式。

## 6. 最小化采集

- 不采集真实姓名，除非后续业务明确需要。
- 手机号和邮箱均为可选字段。
- 不采集地理位置、通讯录、相册等无关权限数据。
- 设备指纹只能保存哈希或随机设备 ID。
